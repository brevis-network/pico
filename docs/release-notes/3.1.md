# Pico 3.1 release notes

Version `3.1.0`, tag `v3.1.0`.

## Highlights

- **128 bits of provable soundness.** Every proof targets 128 bits of provable round-by-round
  soundness under the random-oracle model, through the compress proof (the final proof): riscv
  128.32, convert, combine and deferred 128.39, compress and embed 128.05. Challenges are drawn from
  the degree-5 extension KoalaBear⁵ (`X^5 + X^2 - 1`) in place of KoalaBear⁴, and every layer's
  parameters are set for 128 bits. The number is computed by the repository's soundness calculator
  and recorded in its soundness manifest; it is a computed bound, not a formal verification. The
  on-chain Groth16 step is held to BN254's security level. See
  [docs/soundness](../soundness/README.md).
- **A final compression layer.** COMPRESS re-proves the complete combine root at a preset tuned for
  size, into the final proof: 299,179 bytes (292.17 KiB) in whitelist mode, where the combine root
  alone is 715.80 KiB (3.0's, in whitelist mode, was about 498 KiB). The EVM path goes on from it:
  EMBED re-proves the compress proof under the BN254-hashed config, and WRAP and Groth16 follow.
- **GPU prover.** The RISCV, CONVERT, COMBINE and COMPRESS phases prove on NVIDIA GPUs through
  `distributed-vm`'s `mle-single-node` (`single_node_mle.sh`): the `cuda-mle` device backend runs
  LogUp-GKR, zerocheck, stacked reduction and WHIR, and `gpu-api` generates the chips' traces. The
  CUDA kernels are in [pico-gpu](https://github.com/brevis-network/pico-gpu). GPU proofs verify with
  the CPU verifier.
- **One tree for both provers.** The default build is the CPU prover and needs no CUDA Toolkit or
  GPU, on Linux and macOS. The `cuda` feature (`--features pico-vm/cuda,distributed-vm/cuda`)
  builds the GPU prover; it needs the CUDA Toolkit on x86-64 Linux and an NVIDIA GPU to run, and
  does not fall back to the CPU.
- **Multi-card proving.** `mle-single-node` proves on one or more cards of one host
  (`single_node_mle.sh <cards>`).
- **Two-host proving and ethproofs entry points.** `two_machine_mle.sh` splits a proof across two
  hosts, `mle-ethproofs-single-node` proves Ethereum blocks for the ethproofs service (to the
  combine root) and `mle-ethproofs-vk-bundle` exports its keys. Both carry over from the 100-bit
  prover: this release builds them but has not run them end to end with the 128-bit parameters.
- **Execution history.** The emulator writes one execution history per chunk, a row per executed
  instruction plus its memory and register accesses, in place of the per-chip event streams. Every
  RISC-V chip's trace is built from it, on the card in a `cuda` build, so the GPU prover pins far
  less host memory and copies far less to the card per chunk.
- **Guest runtime for zkevm-standards.** `_start`, the linker script `pico.ld` and one memory
  layout; the `read_input` / `write_output` IO interface with C ABI; `cargo pico lib` writes
  `libpico_zkvm.a`, a static library for guests built without `cargo pico build`. Guests in C and
  C++ build against it with GNU ld or LLD ([`examples/c-guest`](../../examples/c-guest)). A guest
  no longer compiles any of `pico-vm`. See [the guest runtime](../guest-runtime.md).
- **The runtime's memory functions.** A guest always uses the runtime's `memcpy` and `memset`, and
  `cargo pico build` checks that the link kept them: a guest whose `memcpy` or `memset` is another
  definition is refused at build time (see "Memory functions" in
  [the guest runtime](../guest-runtime.md)).
- **One result for every abnormal end.** A non-zero exit, a panic, `abort()`, a failed `assert()`,
  running out of heap and the faults the emulator detects all reach the host as
  `EmulationError::AbnormalTermination`, with a reason and the exit code a native process would
  get.
- **RISC-V conformance.** `FENCE` executes as a no-op, and the ACT4 architectural tests for
  RV64IM_Zicclsm run in CI ([`act4/`](../../act4/README.md)): the 64 tests of the I and M suites
  pass; the 8 Misalign tests fail, since Pico rejects misaligned loads and stores.
- **Host API.** [`pico-verifier`](../../verifier) verifies a whitelist-mode combine root on stable
  Rust without `pico-vm`; `pico-prover` gains the shipped whitelist, the vk bundle, the in-memory
  v3 export, an execute-only cost estimate, and GPU proving behind its `cuda` feature.

## Which proof you get

The phases are RISCV → CONVERT → COMBINE → COMPRESS → EMBED → WRAP, each built from the one before
it. The compress proof is the final, smallest proof; COMBINE is still the default stopping point
everywhere:

| entry | default | to get the compress proof |
|---|---|---|
| `cargo pico prove` | `--phase combine`, `proof-combine.pico` | `--phase compress` (`proof-compress.pico`) |
| `pico-prover` | `Prover::prove` returns the combine root | `prove_to(Phase::Compress)` |
| `single_node_mle.sh` | `MLE_STEP=combine` | `MLE_STEP=compress` |

`prove_evm` and `--evm` always go through COMPRESS and EMBED. `pico-verifier`, `Proof::export_v3`
and the ethproofs entry points handle the combine root only (at least 128.32 bits through the chain
beneath it); a compress proof is verified by `pico-vm`'s apex, or by `pico-prover` in whitelist
mode.

In a `cuda` build of `pico-prover`, a whitelist-mode `prove` (to the combine root) runs on the
multi-card GPU pipeline; any other mode or phase proves its RISC-V chunks and the compress proof on
card 0 and CONVERT and COMBINE on the CPU. `single_node_mle.sh` proves on the GPU up to the combine
root or the compress proof (`MLE_STEP`), verifies on the host, and does not write the proof out.

## Parameters

| layer | RS rate | proximity regime | WHIR queries | soundness |
|---|---|---|---|---|
| riscv | 1/2 | unique decoding | 261, 119, 110, 109 | 128.32 bits |
| convert, combine, deferred | 1/4 | unique decoding | 160, 114, 109 | 128.39 bits |
| compress, embed | 1/16 | list decoding, `m = 2` | 65, 34, 24 | 128.05 bits |

The Groth16 wrap circuit has 7,243,820 R1CS constraints in whitelist mode, the same for every
program (13.6% under 2^23); `verifyProof` costs about 347,000 gas and `verifyPicoProof`
359,000–361,000, depending on the public values. Setup
and the verifier contract change with it: see [`gnark/README.md`](../../gnark/README.md).

## Performance

GPU prover, four RTX 5090 cards in one host, whitelist mode, over the 80 Ethereum blocks around the
99th percentile of the 7,200-block window 24000000–24007199. They were proved with
`sweep_reth_mle.sh`: one resident `mle-single-node` per half of the corpus, the reth guest compiled
ahead of time (`aot-emulator`, with `bigint-rug tcmalloc mmap-memory`), `MLE_VERIFY=0` (intermediate
proofs not re-verified on the host), a warm-up block proved first and not counted, and process
setup not counted. The time runs from a block's input being ready to the compress proof existing.
The window's 99th percentile is its 73rd-slowest block, the 35th slowest of these 80:

| | to the combine root | to the compress proof |
|---|---|---|
| 99th percentile of the window | 8.47 s | 8.60 s |
| mean of the 80 | 8.42 s | 8.55 s |
| slowest of the 80 | 10.02 s | 10.14 s |

In a paired, interleaved measurement during development, on the same four cards and corpus with the
whitelist off, an earlier build of 3.1 took 13% longer than the 100-bit GPU prover (the parameters
of 3.0 and of the 3.1.0-gpu.1 preview) to the combine root, and 15% longer to its final proof (the
100-bit combine root against the 128-bit compress proof). With the whitelist on for the 3.1 build
only (the 100-bit build stayed off), measured the same day but not interleaved, the figures were 15%
and 16%. On the CPU prover, an earlier build of 3.1 took 17–25% longer end to end than with 3.0's
parameters on fib-10 and two reth blocks in whitelist mode.

## Compatibility

3.1 changes the proof system's parameters: no proof, key, whitelist or verifier contract carries
over from an earlier version. What changes depends on where you come from.

| from | its whitelist root | leaves |
|---|---|---|
| `v3.0.0`, the `v3.1.0-gpu.1` preview, and builds of `main` before #125 (version 3.1.0 from #119 on; ere 0.20 pins one of them, `613d6aeb`) | `822417522 744100887 1298155482 1623973239 734555938 1733333192 935892639 781849437` | 15,680 |
| a build of `main` at #125 (`35e639b2`), the last commit before the tag | `1824906095 1504833744 1546273129 1731347331 824402171 1108620310 596927438 916067262` | 15,683 |
| **`v3.1.0`** | `1216878882 1112908309 718797239 1060637411 22230319 902859945 1600756132 39358577` | 15,684 |

### From 3.0

- **The proof system's parameters.** The extension field is KoalaBear⁵, and the parameters, the
  verifying-key whitelist (`vm/src/mle/shape_vk_bins/`) with its root, the soundness manifest, and
  the Groth16 circuit, keys and verifier contract all change. The proof codec is version 5 (it was
  4) and the `.pico` container version 3 (it was 2): older proofs and files are refused, and 3.0's
  verifier refuses 3.1's. A deployment that pins the root (`MLE_VK_ROOT`, a verifier contract)
  needs the new one, and an on-chain verifier needs a new setup and contract.
- **`Phase::Compress`** sits between `Combine` and `Embed`, so an exhaustive `match` on `Phase`
  needs the new arm; `prove_evm` goes through it.
- **`pico-vm`'s `MleApexVerifier::new` and `with_members` take the compress preset**
  (`compress_params`) after the recursion params, so the apex can verify compress proofs as well as
  combine roots; `pico_verifier`'s type of the same name is unchanged.
- **Guests must be rebuilt, and every program id changes.** The new `_start`, memory layout and
  runtime change every guest ELF, so a guest rebuilt for 3.1 has a new program id. A guest whose
  `memcpy` or `memset` is not the runtime's no longer builds.
- **A guest built without `cargo pico build` must link with `pico.ld`**, which
  `cargo pico lib --output <dir>` writes beside `libpico_zkvm.a`, in place of a fixed text address
  such as `-Ttext=…`: `_start` and the heap allocator read its symbols. See
  [the guest runtime](../guest-runtime.md).
- **A guest's abnormal end is `EmulationError::AbnormalTermination`**, with a reason and an exit
  code. It replaces `Unimplemented`, `HaltWithNonZeroExitCode`, `InvalidMemoryAccess` and
  `Breakpoint`.
- **Emulation runs on the snapshot pipeline by default** (up to 16 replay workers, in place of
  3.0's one interpreter). `ProverBuilder::serial_emulation` and `--serial-emulation` emulate on one
  thread as 3.0 did, and `Prover::emulation_workers()`, now without the `aot` feature, returns
  `None` for them.

### From the 3.1.0-gpu.1 preview

Everything under "From 3.0", and:

- The default build no longer needs CUDA, and executing or proving on the CPU no longer needs a
  GPU. Build with `--features pico-vm/cuda,distributed-vm/cuda` for the GPU prover: the `cuda-mle`
  feature is now `cuda`, and the empty `gpu` feature is gone.
- `GPU_TARGET_ARCHS` is gone; use `CUDA_ARCH`.
- **`MLE_EVENT_POOL_SIZE` is now `MLE_HISTORY_SLOTS`**, the records the GPU prover holds at once,
  each in a pinned history slot of about 0.7 GB; the default is 64 (128 in `two_machine_mle.sh`).
  The former name is still read, with a warning, but it now counts slots, not event buffers: a
  value sized for the preview's buffers (such as 256) asks for far more pinned memory. In
  `pico-prover`, `gpu_event_pool_size` sets the same count, and without it the count is sized to
  the host's memory (a quarter of it, between 4 and 32 slots). The slots are pinned on the first GPU
  prove and stay pinned at that count for the life of the process.
- Without `PICO_GPU_MEM` the memory tier is now 32 GB (it was 24 GB); set `PICO_GPU_MEM=4090` for
  24 GB cards.
- macOS builds again (the CPU prover).

### From a build of `main` before the tag

`main` carried version 3.1.0 before this release with the 3.0 proof system. Which root a build had
depends on the commit (table above): builds before #125 carry 3.0's root and lack the guest runtime
and execution history. Everything under "From 3.0" applies, and:

- Builds before #125 read `MLE_EVENT_POOL_SIZE`: see `MLE_HISTORY_SLOTS` under the preview.
- In builds from #123 (including ere 0.20's pin) to #124, `Prover::emulation_workers()` returned
  `NonZeroUsize`; it returns `Option<NonZeroUsize>` now, as described under "From 3.0".
- A CLI installed from that `main` reports the same version as this release's but is not it:
  reinstall it from the tag. `cargo install --list` shows where a CLI came from; only one installed
  with `--tag v3.1.0` (it shows `?tag=v3.1.0`) or from a checkout of the tag is this release.
- In builds from #123 on, `pico-vm`'s `MleApexVerifier` was a re-export of
  `pico_verifier::apex::MleApexVerifier`; it is its own type again, which also verifies compress
  proofs. `pico-verifier` verifies combine roots as before.

## Building the GPU prover

- `make build` and `single_node_mle.sh` pick the GPU build when they find `nvcc` and a GPU;
  `PICO_CUDA=0` or `PICO_CUDA=1` overrides that (see [`detect_cuda.sh`](../../detect_cuda.sh)).
  `ethproofs_single_node_mle.sh` is GPU only.
- `CUDA_ARCH` picks the GPU architectures to build for, for example `CUDA_ARCH=89` or
  `CUDA_ARCH=89,120`.
- The GPU prover's memory thresholds are calibrated on 32 GB cards (RTX 5090); `PICO_GPU_MEM=4090`
  selects the 24 GB tier.

See the [requirements](../requirements.md) and the [support matrix](../support-matrix.md).

## Notes

- The CLI takes Pico from the `v3.1.0` tag for `cargo pico aot`, `--aot` and `cargo pico lib`,
  unless `PICO_SOURCE` names a checkout. `cargo pico new` uses the template's `v3.1.0` (or
  `evm-v3.1.0`) tag when the template repository has it, and otherwise falls back to its `main`
  (or `evm`) branch and says so; until the template repository carries `v3.1.0`, those branches are
  written for Pico 2.1.1 and do not build against this release.
- The Groth16 keys `cargo pico prove --evm --setup` makes, and the verifier in
  `contracts/test/dev`, come from a test setup: a deployment needs keys and a verifier from a real
  setup ceremony.
