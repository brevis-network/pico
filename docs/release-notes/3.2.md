# Pico 3.2 release notes

Version `3.2.0`, tag `v3.2.0`: everything since `v3.1.1`. The tags `v3.1.2` to `v3.1.6` were cut
from `main` along the way, still at version `3.1.1`, and what they carry is described here too. It
is a breaking release: 3.1 proofs and keys are not accepted (see Breaking).

## Breaking

- **New keys and whitelist.** Misaligned loads and stores are now proved (a new `MemoryUnaligned`
  chip), and every store, a precompile's write included, proves it misses the program's code. Every
  convert verifying key changes, and the whitelist is rebuilt: its root is
  `MLE_VK_ROOT` in `vm/src/mle/shape_vk_bins/mle_vk_root.txt`. A proof made by 3.1.x does not
  verify here, nor the other way round.
- **Execution follows the RISC-V target's rules.**
  - A load or store whose address is not a multiple of its width runs (Zicclsm), and is counted:
    `Execution::misaligned_accesses`, `PureExecution::misaligned_accesses` and
    `Proof::misaligned_accesses`.
  - An access ends the run below `0x1_0000` (`NullAccess`), in the stack guard (`StackOverflow`),
    past the top of memory (`InvalidMemoryAccess`), and, for a store, in the program's code
    (`StoreToCode`). A syscall's buffers are checked the same way.
  - A jump or taken branch to a target that is not 4-aligned ends the run at the jump
    (`MisalignedJumpTarget`); a target outside the program, 0 included, or running past the last
    instruction ends it too (`OutsideProgram`). A run ends normally only at `HALT`.

  See [docs/guest-runtime.md](../guest-runtime.md) for the exit codes.
- **ELF validation.** The loader rejects an ELF32, a segment both writable and executable, an
  execute-only segment, and an entry point outside the executable segments.
- **`execute` is pure execution.** It runs the guest to its halt without the proving pipeline; the
  previous `execute` is `execute_chunked`. Both follow the rules above and agree on the committed
  bytes, the cycles, the misaligned-access count and the reason a run ends.
- **AOT code must be regenerated.** `AOT_CODEGEN_STAMP` is 8, and the pure-mode ABI is version 2:
  run `cargo pico aot` again, and rebuild cached pure-mode libraries.
- **The catch-all shape is refused.** A chunk that fits no whitelist shape but the catch-all
  (m = 31, too large to prove in practice) ends the prove with `ProveError::CatchAllShape`: on
  the CPU before anything is proved, where it used to run out of memory, and on the GPU, where it
  used to panic; the GPU pipeline drains and the next prove runs normally. `MLE_FORCE_CATCH_ALL=1` still proves it on the CPU.
- **`cargo pico execute` exits 2 when the run cannot be executed** (a bad ELF, missing input, a
  failed AOT helper build), where it used to exit 1. Status 1 now means only that the guest
  failed: a non-zero exit, a panic, a fault, or a syscall it may not make.
- **Rust guests link the toolchain's prebuilt `std`.** `cargo pico build` no longer builds `std`
  from source when the toolchain ships one, so a guest builds offline, as other zkVMs' guests do;
  `pico-sdk` supplies the `__atomic_*` functions that `std` calls. The guest's ELF, and so its
  program vk, now depends on whether the installed toolchain ships a prebuilt `std` (the build
  prints which it used): with one, a rebuilt guest's ELF changes.
- **GPU kernels.** The `cuda` build needs the kernels `Cargo.toml` names: they fill the
  code-range and stack-guard columns and take the segmented GKR input; the 3.1 kernels do not
  match this tree.
- **Cross-chunk consistency is a global LogUp; the keys and the whitelist change again.** The
  chunks' cross-chunk events (memory and syscalls) used to be summed on a curve, and the sums
  added up outside the proof tree. Now each chunk commits its events as a table, the challenges
  are drawn once every table of the run is committed, group proofs take the tables through one
  LogUp, and the tree's root asserts that it sums to zero
  ([docs/soundness/README.md](../soundness/README.md)). The curve and its chips are gone. Every
  key changes and the whitelist is rebuilt, with a leaf for each node the global LogUp adds to
  the tree; a proof made before this change does not verify here, nor the other way round.
  - A run whose chunks hold more cross-chunk events than one proof may count is refused: on the
    GPU pipeline with `ProveError::TooManyGlobalRows`, before its tree is proved; on the CPU
    where the RISC-V proofs are verified, as `ProveError::Verification`. A p99 Ethereum block
    reaches under 4% of the limit.
  - A program's initial memory image is committed as one table of at most 2^22 words (32 MiB of
    initialized data) at the default stacked height, and of at most 2^h words at
    `log_stacked_height(h)` below 22. `ProverBuilder::build` refuses a larger one with
    `ProveError::InconsistentOptions`.
  - In whitelist mode a recursion program holds each child's key to the row its slot reads:
    the row's key pre-hash is a constant of the program, where the program used to take the
    child's pre-hash from its witness and check that the key was a whitelist member. A key of
    another row is no member there.
  - Formats and types that changed with it: the VK bundle is version 3 (`pico-verifier`'s
    `VmVk` has 20 limbs where it had 25: the image table's commitment and tier in place of the
    initial sum), so a deployment's bundle is generated again; a proof's codec version is 6 and
    a stored `Phase::Riscv` artifact (container version 4) carries the second phase's proofs, so
    one stored before this change is refused by its version; `VerifyRiscvError` has `GlobalLogUp`
    and `NotARiscvMachine`, and no `CrossChunkMemoryInconsistency`.
  - In a `cuda` build the SDK's default chunk concurrency is 1 where it was 4: it now follows
    the VM's default, and a card proves one chunk at a time.
  - Below the default stacked height a chunk's table is smaller, 2^(h-1) rows at
    `log_stacked_height(h)`, while the emulator still cuts its records for the default's 2^22. A
    program whose record holds more cross-chunk events than the table (one that touches more
    than 2^(h-1) memory words in all, for one) stops with "more cross-chunk events ... than a
    Global table ... holds", and proves at a higher stacked height.
  - On two machines (`two_machine_mle.sh`) each machine commits the tables of the chunks it
    proves: the secondary reports its commitments to the primary and follows the primary's, each
    machine proves the group proofs over its own tables and their nodes, and the primary reduces
    both machines' nodes. The scheduler's gRPC service has three messages for it, so the two
    machines run the same build. A two-machine run to `--step riscv` or `--step convert`, which
    never completed, is refused at start.
  - On the CPU each chunk's table has 2^22 rows at the default stacked height whatever the
    program, and a chunk being proved holds about 2 GB for it: fibonacci proves to the compress
    proof in about 6 GB one chunk at a time and under 8 GB two at a time on 16 cores, 9.4 GB on
    124. The default concurrency, 4 in 3.1, is lower on a small host: 3 under 20 GiB of memory,
    2 under 16, 1 under 12 ([docs/requirements.md](../requirements.md)).
  - On the CPU `ProverBuilder::concurrency` (and `PROVE_CONCURRENCY`) now also bounds the
    recursion proofs: the convert proofs and the nodes of a tree layer are proved that many at a
    time, where every chunk's convert proof used to be proved at once. A program of many chunks
    peaks lower for it, and at `concurrency(1)` one proof is proved at a time throughout. Key
    generation is not bounded: the convert programs of a run, one per distinct chunk shape, are
    still keygen'd together. A `cuda` build is unchanged.

## Added

- **Compress proofs verify in `pico-verifier`.** `verify_compress` / `verify_compress_with` take a
  compress proof as a v5 envelope (`Proof::export_compress_v5`), with the checks `verify` runs on
  a combine root; neither entry point accepts the other's envelope. The envelope holds the proof
  alone: the whitelist has one compress key, which `pico-verifier` ships
  (`shipped_compress_vk`, from `vm/src/mle/shape_vk_bins/mle_compress_vk.bin`). Its WHIR Merkle
  openings travel as multiproofs, about 13% smaller before zstd and 5% after; the decoder rebuilds
  the flat proof, so the verifier, the circuits and every key are unchanged.
- **Compress on the GPU.** In a `cuda` build, a whitelist-mode `prove_to(Phase::Compress)` proves
  the root on the multi-card GPU pipeline, as `prove` does, then the compress layer on card 0.
- **The ethproofs entry submits compress proofs.** With `MLE_STEP=compress` (whitelist mode,
  `VK_VERIFICATION=true`), `mle-ethproofs-single-node` answers each block with its compress proof as
  a v5 envelope, typed `COMPRESS`, which `pico_verifier::verify_compress` checks under the cluster's
  VK bundle (the bundle already carries the compress key's membership). `MLE_STEP=combine`, the
  default, still submits the v3 root. RSP needs no change.
- **`cargo pico execute` serves a test harness.** `--public-output <file>` writes the committed
  bytes, `--exit-code-file <file>` the guest's exit code, and `--pure` runs the guest without
  chunking it, in constant memory.
- **BLS12-381 G2 add and double precompiles.** `BLS12381_G2_ADD` and `BLS12381_G2_DOUBLE` add and
  double affine G2 points, and `zkvm_bls12_g2_msm` runs bls12_381's multiexponentiation, which
  calls them. The eth-act standards test `accel-bls12-g2-msm` proves in
  about 355 s on one RTX 5090, where it took about 3,956 s.
- **A BLAKE2b rounds precompile.** `BLAKE2B_ROUNDS` runs up to 1,000 rounds of BLAKE2b's schedule
  on a working vector in guest memory, proved at a row a round (`syscall_blake2b_rounds` in
  `pico-sdk`), and `zkvm_blake2f` runs EIP-152's F on it inside the zkVM. In software a round is
  about 253 instructions and F's round count is the caller's: mainnet block 26426155, whose one F
  call runs 10.5 M rounds, goes from 2.89 billion cycles to 234 M in a reth guest that calls the
  precompile.
- The `zkvm_accelerators.h` functions in `libpico_zkvm.a` (`examples/c-accelerators`).
- `malloc` for C guests on newlib, through the runtime's `sbrk`, which shares its heap with the Rust
  allocator (`examples/c-guest/malloc.c`).
- ACT4 `RV64IM_Zicclsm`: all 72 tests execute, prove and verify.
- **A second reth guest, for Ethereum's Amsterdam fork.** `MLE_ELF=reth-amsterdam` (`--elf
  reth-amsterdam`) makes `mle-single-node` and `mle-ethproofs-single-node` prove
  `perf/bench_data/rv64/reth-amsterdam-elf`: RSP's client on reth v2.11.0 and evm2, which executes
  blocks of the fork and mainnet before it. `reth`, the default, and `reth-elf` are as they were.
  An input of one guest is not an input of the other
  ([docs/how-to-setup-gpu-machine.md](../how-to-setup-gpu-machine.md)).

## Performance

- The global LogUp takes less GPU work than the cumulative sum it replaces: on four cards the p99
  corpus proves to its compress proof in 8.06 s a block on average against 8.30 s, with 12% fewer
  lane-seconds. The core and convert ladders are refitted for it.
- The AOT replay workers run recording blocks that write the records themselves.
- The chunk split counts what a precompile costs the RISC-V chunk, not each of its memory accesses.
- The GPU pipeline holds 16 history slots by default.
- `memcpy`, `memset`, `memcmp` and `bcmp` are new RV64 assembly in `pico-sdk`, with aligned
  accesses only: `memset` stores 8 bytes at a time instead of 4, `memcpy` shifts words into place
  instead of copying bytes when the source and destination sit at different offsets, and `memcmp`
  (now also linked into Rust guests) compares words instead of bytes. The reth stateless guest of
  the EF p99 benchmark retires 6–9% fewer instructions.
- `zkvm_modexp` runs a modulus of at most 256 bits, behind any zero bytes, on the `UINT256_MUL`
  precompile instead of in software. The reth stateless guest of the EF p99 benchmark retires 21%,
  41% and 14% fewer instructions on blocks 24004465, 24005809 and 24006427, whose modexps are all
  modulo BN254's scalar field order.
- `cargo pico build` compiles guests with `-C target-feature=+unaligned-scalar-mem`: the compiler
  reads and writes whole words at misaligned addresses, which Pico proves, instead of putting
  values together a byte at a time. The reth stateless guest of the EF p99 benchmark retires
  19–20% fewer instructions, in 13–15% fewer cells. A CPU chunk proves its misaligned accesses at
  2^10, 2^16, 2^17, 2^18 or 2^19 `MemoryUnaligned` rows, the smallest that holds them, where it
  had 2^10 and closed at the 1,024th; each core ladder row is a whitelist shape at each height.
  `--rustflags="-C target-feature=-unaligned-scalar-mem"` builds without it.
- A guest depending on `pico-sdk` no longer locks the prover: `pico-vm` is behind the `prover`
  feature and `init_logger`'s crates behind `logger`, on by default. A minimal guest's lockfile
  goes from 372 packages to 129, or 107 with `default-features = false`.

## Fixed

- Under the whitelist a guest's instruction mix no longer leaves a CPU chunk without a shape. A
  whitelist prover has the chunk split close a chunk while a row of the core ladder still holds it
  (`EmulatorOpts::ladder_fit`, which the SDK sets with `verify_keys` and `distributed-vm` in
  whitelist mode; a caller that builds `EmulatorOpts` field by field states it). The split did not
  look at the rows of the arithmetic tables, and a chunk no row held ended the prove with
  `ProveError::CatchAllShape`, or with a panic when it had outgrown the catch-all too, as a chunk
  more than half of whose instructions are comparisons and branches has. A program whose chunks
  all take a ladder row is cut where it was. One whose mix leaves the ladder proves, cut into more
  chunks than without the whitelist: Fibonacci, whose loop has four Add rows in every six
  instructions, closes a chunk at 2^22 Add rows, after 6.3 M instructions, where the clk limit
  closes it at 8.4 M. Without the whitelist nothing changes.
- `build_pure_library` builds the generated crates against the lockfile of the Pico checkout
  `pico-prover` was compiled from, rather than whatever versions the registry has that day. The
  lockfile is version 4, so the build needs cargo 1.78 or later; the lockfile joins the library
  cache key, so libraries cached by an earlier version rebuild once.
- `build_pure_library` is safe for processes or containers sharing one cache: one builds a key
  under a file lock while the others wait, scratch names no longer repeat across containers that
  all run as pid 1, and the library is synced before it is renamed into place. The key also holds
  the toolchain (`rustc -vV`), so even a cache hit needs `rustc`; the build is for the host and
  ignores `RUSTFLAGS`, `CARGO_BUILD_*` / `CARGO_PROFILE_*` / `CARGO_TARGET_*` and config
  `rustflags`; and a dead build's scratch directory is cleared once its key's lock is free.
  `ProverBuilder::disable_pure_aot` turns pure mode off without the missing-program warning.
- Below 500 GB of host memory, or in a container capped below it, the GPU prove defaults to 2
  replay workers, 4 history slots, 4 emulator memories and 8 waiting deferred records, so the
  eth-act standards tests prove within 128 GB. `PICO_HOST_MEM=low|high` overrides the tier.
- A GPU prove reuses the riscv keys `ProverBuilder::build` made instead of keygenning the program
  again, about 6 s less per new program.
- The pipeline's emulation, CPU-only builds included, runs at most `MLE_DEFERRED_RECORDS` (512; 8 below 500 GB of host memory) deferred (precompile and
  memory) records ahead of proving them, as the history slots bound it on CPU chunks. A
  precompile-heavy guest used to queue them without limit: BLS12-381 G2 MSM grew past 500 GB of
  host memory. `0` lifts the bound.
- A GPU prove whose emulation is finalized after its proof tree collapses, as when a large guest's
  memory takes long to free, proves its root, on one machine or two: the scheduler holds back a
  node over every chunk registered so far until the emulation is finalized. It used to be built as
  an inner node, and the run failed with "no final combine node was recorded" or waited out the
  scheduler's 300 s timeout.
- A card running out of memory in an embedded GPU prove usually leaves the process able to prove.
  The pipeline drains the run, drops the recursion keys the run added, and the prove returns
  `ProveError::GpuOutOfMemory` if the drain left everything as the run found it. Otherwise, and
  after any other failed stage, the process is poisoned as before: a card with an error pending,
  history slots still held, or a card's pools above where the run started.
- The BLS12-381 accelerators (`zkvm_bls12_*`, `zkvm_kzg_point_eval`) refuse a field element at or
  above the modulus before the curve library parses it. The library's parser multiplies even a
  value it then rejects, and inside the zkVM that multiplication is a field syscall that cannot be
  proved with such an operand: a guest that passed one ran, and was refused correctly, but its run
  could not be proved.
- A `distributed-vm` binary built with AOT crates stops when it loads an ELF other than the one the
  crates were generated from, and names both digests. It used to run that ELF through the other's
  compiled code and fail somewhere inside a proof.
